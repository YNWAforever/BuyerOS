## 2. Primary recommendation

Use A as a **selective MIT adaptation source** for bounded insight, keyword and company extraction logic, after dependency licensing and security review. Implement BuyerOS-owned contracts, evidence records, approvals, contact gates, money ledger, tenant checks and durable work scheduling around those pure capabilities. Preserve the existing BuyerOS frontend. Do not transplant A's frontend, API server, state store, shared token authentication, job queue or mail automation.

Keep F/R integration **DEFERRED AND BLOCKED** pending a component/distribution license decision, demonstrated value on the account-first pilot, and verified provider/data terms. F is a person-oriented licensed-data discovery product; it is not a drop-in evaluator for arbitrary BuyerOS company rows. Its plain-language fit-reason concept is useful, but copying its implementation or prompts is a licensing decision. A separate process, container or worker is not, on its own, a conclusion that GPL obligations are resolved. Evaluate the actual integration, distribution and license notices with a qualified reviewer before adopting it.

S is separately MIT, but its operational sender is **P7 ONLY** and not needed for the research/contact/draft pilot. Do not infer that all OpenOutreach-family code is GPL or all is MIT. The package dependency graph and the selected copied files both need a notice/SBOM inventory.

## 5. Actual public interfaces: do not invent integration commands

These are **source observations, not commands authorized to execute**:

- A's node imports are rooted at its `backend` Python path: e.g. `agents.insight_agent.insight_node`, `agents.keyword_gen_agent.keyword_gen_node`, `agents.search_agent.search_node`, `agents.lead_extract_agent.lead_extract_node`, `graph.evaluate.evaluate_progress`, and `agents.email_craft_agent.email_craft_node`. They are not an installable BuyerOS SDK. Their global settings/tools and module imports are coupled and need extraction/dependency injection before adaptation.
- A `build_graph` accepts explicit node callables and checkpointer, but compiles missing nodes to no-ops. Do not use a successful compile as proof capabilities are wired.
- F defines `outfind = "openoutfind.__main__:main"`. The verified `find` options include count, optional leads/emails unit, `--new`, `--emails`, `--json`, `--batch`, `--open`, log level/debug and agent-qualification options. This audit does not propose wrapping them into a production command. The later pinned command also allows a pending verdict to be returned to the finder; that is a verdict-resume mechanism for an internally selected candidate, not a generic company import.
- F JSONL contains `email`, `first_name`, `last_name`, `company`, `title`, `website`, `linkedin_url`, `reason`, `lead_id`, `qualified_at`, `profile_text`. CSV excludes `profile_text`. No score field is exported. `reason` belongs to the model's verdict. Human acceptance must be newly recorded in BuyerOS.
- S defines `outsend = "cold_outreach.__main__:main"`, reads JSONL stdin when no command is supplied, and exposes `send`/`check` in its actual parser. A docstring mentions historical init wording, but parser inspection is the authority; do not invent a currently supported init command.
- R `_run` calls Django `find` in paid `emails` mode, takes its JSONL in an in-memory buffer, invokes S `ingest`, and then `_send`. It is unsuitable as a draft-only pilot worker.

## 7. Minimum reusable evidence and mandatory new tests

Useful A tests show bounded keyword generation, maps-only routing, official-domain dedupe, lead target stopping, locale rules, schema failure fallback, queue claim/recovery and event formatting. They do **not** establish BuyerOS multi-tenancy, a paid-operation financial invariant, exact approval binding or durable replay. Useful F/S tests establish their own CLI/JSONL/replay/suppression contracts but do not establish BuyerOS's permitted-purpose, human acceptance and content-approval policy.

Before any selected capability ships, require these BuyerOS-owned tests with deterministic provider fixtures:

1. Approved offer/profile ID is pinned into the research run; changes never silently rewrite previous evidence/fit.
2. LLM cannot authorize new URLs/tool types/spend, and webpage instructions cannot cause a network call or disclosure outside the fetch policy.
3. Fact output references allowed evidence IDs; unknown evidence is rejected, not converted to a claim. Insufficient evidence produces Needs review.
4. Company fit, reviewer acceptance, mailbox validity, suppression, research permission, outreach permission, draft approval and delivery remain independently stored and gated.
5. Concurrent quote confirmations reserve at most once; identical key/different hash conflicts; expired quotes cannot reserve; confirmation and worker both recheck policy/suppression/fit freshness.
6. Worker death or timeout after possible provider acceptance creates unknown submission state, retains upper-bound reservation, does not blindly resubmit, and exposes reconciliation work. A late result cannot expose prohibited data after policy revocation.
7. Known provider handle polling survives restart; duplicate/out-of-order result events cannot double-charge or resurrect a canceled/revoked action.
8. Exact content/recipient/evidence/profile/policy fingerprint approval is invalidated by material edits or changed policy/suppression; optimistic concurrency prevents stale editors preserving an approval.
9. In live mode, provider failure yields a typed failure/partial result; never demo fixtures. Synthetic anchors/fixtures remain outside live company/contact/usage tables.
10. Pilot API has no enabled send/schedule behavior, no mailboxes, no network route to the OpenOut contacts hub and no secret-bearing settings writes.
