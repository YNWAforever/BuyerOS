## Deviations from the brief

The brief's `pyproject.toml` verbatim **cannot work in this repository**, because `services/api/pyproject.toml` declares no `[build-system]` and no `[tool.setuptools]` stanza. It is a flat-layout project containing `alembic/` (with `env.py`/`versions/*.py`) and `buyeros_api/`, so the setuptools legacy backend fails with `Multiple top-level packages discovered in a flat-layout: ['alembic', 'buyeros_api']`. Any `uv lock`/`uv sync`/`uv run` that must satisfy the `../api` path dependency aborts on that build error.

Alternatives that were empirically tested and **failed** (all confined to `services/worker`):
- `buyeros-api = { path = "../api", editable = true }` → `build_editable` fails, same discovery error.
- `[[tool.uv.workspace]] members = ["../api"]` + `buyeros-api = { workspace = true }` → noted as a package and still built, same error.
- `[tool.uv] no-install-package = [...]` → not a valid `[tool.uv]` key and not accepted by `uv run`.

`services/api` is explicitly out of scope, so the following **three minimal, reversible** deviations were applied to `services/worker/pyproject.toml` only:

1. **Added `"pydantic-settings>=2.5,<3"` to `[project].dependencies`.** `buyeros_worker/config.py` imports `pydantic_settings` directly (it previously only arrived transitively via `buyeros-api`). With deviation 2 in place the transitive path is gone, so the direct import must be declared. This is correct dependency hygiene regardless.
2. **Added `[tool.uv] exclude-dependencies = ["buyeros-api"]`** (with an explanatory `NOTE` comment). The `[project].dependencies` entry and the `[tool.uv.sources] buyeros-api = { path = "../api" }` entry are **kept verbatim as the brief requires**; exclusion only stops uv from trying to build the un-buildable path dependency.
3. **Added `"../api"` to `[tool.pytest.ini_options].pythonpath`** (alongside the brief's `"."`), so `buyeros_api` imports from the `services/api` source tree without installation.

Ordering deviation inside Step 3: `pyproject.toml` had to exist before `uv run pytest` could execute at all (otherwise `pytest` is not spawnable). The RED state was still observed for the right reason (`ModuleNotFoundError: No module named 'buyeros_worker'`) before any `buyeros_worker` module was created.

## Concerns / recommended follow-up

1. **`buyeros_api` is importable in tests only.** Because the `../api` path dependency is excluded from uv resolution, `uv run python -c "import buyeros_api"` fails (`ModuleNotFoundError: No module named 'buyeros_api'`) — only pytest's `pythonpath` entry makes it importable. Any non-pytest entrypoint (e.g. launching the Celery worker process, or `buyeros_worker` runtime imports of `buyeros_api`) will fail until `services/api` is made installable.
2. **Recommended one-line fix (a later task, in `services/api`):** add a packaging stanza, e.g. `[build-system] requires = ["setuptools>=68"] build-backend = "setuptools.build_meta"` plus `[tool.setuptools] packages = ["buyeros_api"]` (or equivalently `packages = ["buyeros_api", "buyeros_api.db", "buyeros_api.providers", "buyeros_api.services"]`). Once that lands, deviations 2 and 3 can be reverted, leaving the brief's `pyproject.toml` exactly as specified; deviation 1 (`pydantic-settings`) should be kept as it is a genuinely direct import.
